System

Tabii kral. Şu an kurduğumuz sistem aslında iki büyük pipeline’ın birleşimi:

  1. Bilgi transferi deney pipeline’ı
    • Sentetik fact’leri İngilizce öğretmek
    • Modeli Türkçeye adapte etmek
    • Türkçe retrieval’ın transfer mi, yeniden öğrenme mi olduğunu ölçmek
  1. Türkçe corpus hazırlama pipeline’ı
    • Türkçe Wikipedia dump’ını güvenli ve tekrarlanabilir biçimde indirmek
    • Temizlemek
    • Sentetik fact contamination’ından arındırmak
    • M2 ve M3 eğitiminde kullanılabilecek hale getirmek

Bunların üstünde de bütün deneyleri çalıştıran:

  • Git/GitHub
  • Conda
  • Hugging Face
  • PyTorch
  • Slurm
  • A100 GPU
  • artifact manifestleri
  • test sistemi

bulunuyor.

1. Araştırmanın temel sorusu

Biz yalnızca:

“GPT-2 Türkçe sorulara cevap verebiliyor mu?”

diye bakmıyoruz.

Asıl soru:

Model önce bazı fact’leri yalnızca İngilizce öğrendiyse ve daha sonra fact’leri içermeyen genel Türkçe veri üzerinde adapte edildiyse, bu fact’ler Türkçe sorular üzerinden erişilebilir hale geliyor mu?

Burada iki olası açıklama var:

Cross-lingual transfer

Fact modelde İngilizce öğrenildi.

Türkçe adaptation sırasında model:

  • Türkçe lexical representations,
  • Türkçe syntax,
  • Türkçe prompt understanding

öğrendi.

Sonrasında model İngilizce tarafında bulunan fact’e Türkçe prompt üzerinden erişmeye başladı.

Relearning

Model fact’i Türkçe adaptation verisinde yeniden gördü.

Bu durumda Türkçe retrieval’ın nedeni cross-lingual transfer değil, Türkçe tarafta fact’in tekrar öğrenilmesi olabilir.

Biz bu iki açıklamayı kontrollü deneyle ayırıyoruz.

2. Deneydeki model aşamaları

Deney dört model durumundan oluşuyor.

M0 — Base model

İlk model:

openai-community/gpt2

Bu model henüz bizim sentetik fact’lerimizi görmedi.

M0’ın amacı:

  • doğal object bias’larını ölçmek,
  • English ve Turkish prompt baseline’ını görmek,
  • chance-level performansı görmek,
  • evaluator’ın doğru çalıştığını doğrulamak.

M0 düşük accuracy verirse bu normaldir. Çünkü sentetik subject’leri bilmiyor.

M1 — English fact acquisition

M0’a bizim sentetik fact dataset’imiz yalnızca İngilizce cümlelerle öğretilecek.

Örneğin sentetik bir subject:

Süreyya Çinpolat

Fact’leri:

Süreyya Çinpolat is a footballer.
Süreyya Çinpolat was born in San Diego.
Süreyya Çinpolat lives in Wichita.
Süreyya Çinpolat studied at the University of Southampton.
Süreyya Çinpolat works at McDonald's.

Model bu fact’leri yalnız İngilizce training data içinde görecek.

M1’in görevi:

  • subject–profession,
  • subject–birthplace,
  • subject–residence,
  • subject–university,
  • subject–employer

ilişkilerini İngilizce olarak parametrelerine yerleştirmek.

Burada önemli nokta:

M1’de İngilizce olarak öğrenilemeyen fact’ler daha sonra transfer analizi için kullanılamaz.

Çünkü model fact’i İngilizcede bilmiyorsa, Türkçede retrieve edememesi transfer başarısızlığı değildir.

M2 — Turkish adaptation, fact exposure yok

M2 şu şekilde üretilecek:

M1
+
temiz genel Türkçe corpus
=
M2

Bu Türkçe corpus’ta:

  • sentetik subject isimleri olmayacak,
  • sentetik training sentence’ları olmayacak,
  • sentetik subject–object ilişkileri olmayacak,
  • fact ID veya dataset artifact’leri olmayacak.

M2’nin temel bilimsel sorusu:

Model İngilizcede öğrendiği fact’i, yalnız genel Türkçe language adaptation sonrasında Türkçe prompt üzerinden retrieve edebiliyor mu?

M2 ana transfer condition’dır.

M3 — Turkish adaptation + Branch B repetition

M3 yine M1’den başlayacak.

M1
+
aynı genel Türkçe corpus
+
Branch B fact’lerinin Türkçe tekrarları
=
M3

Branch A fact’leri Türkçe training’de görünmeyecek.

Branch B fact’leri ise Türkçe olarak tekrar edilecek.

Böylece:

GrupTürkçe fact exposureYorum
Branch AHayırTransfer-only
Branch BEvetRelearning/repetition condition

M2 ve M3 karşılaştırması bize açık Türkçe factual exposure’ın etkisini gösterecek.

9. Candidate scoring adım adım

Örnek Turkish question:

Süreyya Çinpolat nerede doğdu?

City candidates:

San Diego
Wichita
Berlin
Ankara
Paris
...

Evaluator her candidate için tam string oluşturuyor:

Süreyya Çinpolat nerede doğdu? San Diego
Süreyya Çinpolat nerede doğdu? Wichita
Süreyya Çinpolat nerede doğdu? Berlin
...

Daha sonra GPT-2’nin yalnız candidate answer token’larına verdiği olasılık hesaplanıyor.

Prompt token’larının likelihood’ı candidate score’a dahil edilmiyor.

Matematiksel olarak:

[
P(a q)
================

{t=1}^{|a|}
P(a_t q, a{<t})
]

Burada:

  • (q): question prompt
  • (a): candidate answer
  • (a_t): candidate içindeki token

10. Neden boundary-aware tokenization gerekiyor?

GPT-2 byte-level BPE tokenizer kullanıyor.

Şunlar aynı tokenization’a sahip olmayabilir:

"San Diego"

ve:

"...doğdu? San Diego"

Özellikle baştaki space tokenization’ı etkiler.

Bu nedenle candidate’ı bağımsız tokenize edip sonradan prompt’a eklemiyoruz.

Yaptığımız:

  1. Full prompt + candidate string oluşturmak
  1. Bütün string’i tokenize etmek
  1. Offset mapping ile answer span’ını bulmak
  1. Yalnız answer token position’larını masklemek
  1. Logits’ten yalnız o token’ların probability’sini toplamak

Bu, evaluator’ın en kritik teknik detaylarından biri.

11. İki farklı scoring yöntemi

Primary score: mean token log probability

[

{t=1}^{|a|}
P(a_t q,a{<t})]

Bu yöntem answer uzunluğunun etkisini azaltır.

Örneğin:

  • Singer
  • Software Engineer
  • University of Southampton

farklı token uzunluğuna sahip.

Raw sum kullanılırsa kısa cevaplar avantajlı olabilir.

Bu nedenle primary metric mean token log probability.

Secondary score: total log probability

[
{t=1}^{|a|}
P(a_t q,a{<t})]

Bu da sensitivity analysis olarak tutuluyor.

Tezde ana sonuç mean score’dan gelecek, total score ile robustness kontrolü yapacağız.

12. Candidate batching

İlk evaluator her candidate için ayrı model forward pass yapıyordu.

Bu çok yavaştı.

Şimdi candidate’lar batch halinde çalışıyor.

Örneğin:

candidate_batch_size = 64

100 subject pilot için:

  • 500 fact
  • 2 dil
  • relation başına farklı candidate count
  • toplam yaklaşık 158.400 prompt–candidate sequence

üretiliyor.

Batching ile yaklaşık 3.200 model forward batch yeterli oluyor.

PyTorch tarafında:

  • torch.inference_mode()
  • BF16 model forward
  • FP32 log_softmax
  • attention mask
  • answer token mask

kullanılıyor.

Model BF16 çalışıyor çünkü A100 bunu iyi destekliyor.

Fakat probability hesabında numerical stability için:

torch.log_softmax(logits.float(), dim=-1)

kullanılıyor.

İki evaluation config’imiz var.

Primary direct prompt

Bu ana evaluation.

Bunu sensitivity analysis için kullanıyoruz.

Neden iki format var?

Çünkü Turkish prompt’a English Question: / Answer: eklersek, retrieval’ın bir kısmı English scaffold’dan kaynaklanabilir.

14. Evaluator metrikleri

Her fact için:

  • correct candidate rank
  • predicted object
  • top-5 objects
  • correct answer score
  • highest incorrect score
  • score margin
  • candidate count

kaydediliyor.

Aggregate metrikler:

Top-1 accuracy

Doğru cevap rank 1 mi?

Top-5 accuracy

Doğru cevap ilk beşte mi?

Mean Reciprocal Rank

[
MRR = _i ]

Doğru cevap üst sıralardaysa yüksek çıkar.

Mean rank

Doğru cevabın ortalama sırası.

Median rank

Outlier’lardan daha az etkilenir.

Margin

[
score(correct)-score(best incorrect)]

Sadece doğru seçildi mi değil, ne kadar güvenli seçildiğini gösterir.

24. Contamination matcher preflight

Full Wikipedia indirilmeden önce contamination scanner’ın maliyetini ölçüyoruz.

Synthetic dataset’ten bütün pattern’lar oluşturulur:

  • 5.000 full subject name
  • casefold name variant
  • Turkish lowercase variant
  • subject ID’ler
  • fact ID’ler
  • English training sentence’ları
  • Turkish repetition sentence’ları
  • dataset artifact isimleri
  • canonical object surface’leri

Sonra üç matcher oluşturulur:

  1. Exact NFC matcher
  1. Unicode casefold matcher
  1. Turkish-aware lowercase matcher

Preflight raporu:

  • pattern count
  • pattern count by rule
  • pattern count by channel
  • automaton state count
  • inventory build time
  • matcher build time
  • total pattern character count
  • peak RSS memory

verir.

Amaç full corpus’u indirmeden önce scanner’ın RAM’e sığıp sığmadığını görmek.

25. Aho–Corasick contamination matcher

Normal yaklaşım şu olurdu:

her Wikipedia document
× her pattern

Bu aşırı yavaş olur.

Biz Aho–Corasick tipi multi-pattern matcher kullanıyoruz.

Bir trie/automaton bir kez oluşturuluyor.

Daha sonra bir document:

[
O(text length + match count)]

yaklaşık maliyetle taranıyor.

Üç ayrı normalization channel var:

Exact NFC

Unicode NFC uygulanmış exact text.

Casefold

Unicode case-insensitive eşleşme.

Turkish lowercase

Türkçeye özgü:

  • I → ı
  • İ → i

dönüşümleriyle eşleşme.

Bu özellikle Türkçe isimler için önemli.

26. Dump download

Download:

  • streaming
  • resumable
  • .partial file
  • HTTP Range request

kullanıyor.

Download yarıda kalırsa bir sonraki çağrı:

Range: bytes=<existing_size>-

gönderir.

Kod kontrol eder:

  • status 206 mı,
  • Content-Range var mı,
  • range doğru byte’tan başlıyor mu?

Sunucu Range’i görmezden gelip status 200 dönerse mevcut partial’ın sonuna full file append edilmez.

Bu corruption’ı engeller.

Download tamamlandığında dosya henüz:

downloaded_unverified

durumundadır.

27. SHA-1 verification

Wikimedia’nın official SHA-1 checksum’u kullanılır.

Downloaded .partial file’ın SHA-1’i streaming olarak hesaplanır.

Eğer:

observed SHA-1 == expected SHA-1

ise dosya atomik şekilde final adına taşınır.

Aksi halde pipeline fail olur.

Bu aşamadan önce extraction başlamaz.

28. Production parser smoke test

Gerçek full dump extraction’dan önce küçük local .xml.bz2 fixture ile gerçek parser stack test edilir.

Kullandığımız paketler:

mwxml==0.3.8
mwparserfromhell==0.7.2

mwxml:

  • MediaWiki XML dump’ını stream eder,
  • page ve revision yapısını okur.

mwparserfromhell:

  • wikitext’i parse eder,
  • link/template markup’ını temizler,
  • plain text’e dönüştürür.

Smoke test doğrular:

  • namespace filtering
  • redirects
  • page ID
  • revision ID
  • Turkish characters
  • extracted text

29. Extraction aşaması

Input:

.xml.bz2 Wikimedia dump

Processing:

  1. BZ2 stream açılır
  1. mwxml page’leri sırayla okur
  1. Namespace 0 dışındaki sayfalar atılır
  1. Redirect’ler atılır
  1. Current/latest revision seçilir
  1. Wikitext alınır
  1. mwparserfromhell ile plain text çıkarılır
  1. Metadata korunur
  1. JSONL’ye satır satır yazılır

Her document şunları içerir:

  • document ID
  • page ID
  • revision ID
  • title
  • namespace
  • dump date
  • source project
  • extracted text
  • raw wikitext SHA-256
  • provenance
  • disambiguation flag
  • unresolved markup counters

Corpus RAM’e tamamen yüklenmez.

30. Normalization aşaması

Her document satır satır normalize edilir.

Uygulanan işlemler:

  • UTF-8
  • Unicode NFC
  • \r\n → \n
  • invalid control character removal
  • pathological whitespace collapse
  • paragraph preservation
  • bazı residual HTML/markup fragment removal

Korunan şeyler:

  • Türkçe karakterler
  • case
  • punctuation
  • paragraph boundaries

Global lowercase yapılmaz.

ASCII transliteration yapılmaz.

Örneğin:

İstanbul
Şırnak
Çığ
Öğrenci

karakterleri korunur.

Her normalized text’in SHA-256 hash’i alınır.

31. Audit aşaması

İlk corpus run’ında agresif document silmiyoruz.

audit_only kullanıyoruz.

Her document için şu metrikler hesaplanır:

  • character count
  • alphabetic ratio
  • Latin-script ratio
  • URL ratio
  • symbol ratio
  • markup-remnant ratio
  • encoding anomaly count
  • mixed-language heuristic

Sonrasında corpus düzeyinde:

  • min
  • max
  • mean
  • histogram
  • reason counts

üretilir.

Amaç gerçek data dağılımını görmek.

Örneğin min character threshold’ını agent’ın kafasına göre seçmesini istemiyoruz.

Önce audit raporunu göreceğiz, sonra threshold’ları bilimsel olarak donduracağız.

32. Filter aşaması

Audit report incelendikten sonra config’te threshold’lar kesinleştirilecek.

Örneğin ileride:

  • çok kısa document
  • aşırı URL içeren document
  • aşırı symbol içeren document
  • encoding bozuk document
  • aşırı markup kalmış document

çıkarılabilir.

Ama language ID ilk aşamada otomatik removal yapmıyor.

Çünkü source zaten Turkish Wikipedia.

Language ID gerekirse yalnız audit signal olarak kullanılacak.

33. Exact deduplication

Normalize edilmiş text SHA-256 ile exact duplicate bulunuyor.

Bütün hash’leri Python RAM dictionary’sinde tutmak yerine SQLite kullanılıyor.

SQLite table:

content_hash
kept_document_id

Her document geldiğinde:

  1. Hash hesaplanır
  1. SQLite index’te aranır
  1. Hash yoksa document tutulur
  1. Hash varsa duplicate report’a yazılır

Keeper policy:

first document in stable stream order

Near-duplicate removal şu an yok.

Çünkü fuzzy dedup daha fazla complexity ve yanlış removal riski getirir.

34. Contamination scan

Deduplicated corpus, synthetic dataset’e karşı taranır.

Üç output oluşur:

clean_documents.jsonl
removed_documents.jsonl
matches.jsonl

Remove-level eşleşmeler

  • full synthetic subject name
  • casefold full name
  • Turkish-lower full name
  • exact synthetic training sentence
  • subject ID
  • fact ID
  • dataset artifact name
  • subject + own object co-occurrence

Flag-only eşleşmeler

Sadece object adı.

Örneğin:

San Diego
McDonald’s
University of Southampton

gerçek Wikipedia’da doğal olarak bulunabilir.

Bu yüzden yalnız object match document removal sebebi değildir.

Ama:

Süreyya Çinpolat + San Diego

aynı document’ta varsa güçlü contamination evidence’dır.

Her match için:

  • document ID
  • title
  • rule ID
  • pattern ID
  • match channel
  • context snippet
  • associated subject IDs
  • automatic decision

kaydedilir.

35. Clean ve removed document ayrımı

Bir document’ta remove-level eşleşme varsa:

removed_documents.jsonl

dosyasına gider.

Yoksa:

clean_documents.jsonl

dosyasına gider.

Split yalnız:

clean_documents.jsonl

okur.

Bu bilimsel iddia için kritik:

Sentetik fact exposure tespit edilen document training corpus’a giremez.

36. Train/validation split

Split document-level yapılır.

Her document ID için SHA-256 hash hesaplanır.

Hash belirli fraction’ın altındaysa validation, değilse train.

Örneğin:

98% train
2% validation

Bu yöntem:

  • processing order’dan bağımsızdır,
  • tekrar çalıştırıldığında aynı document aynı split’e gider,
  • random shuffle’a bağlı değildir.

Validation document’ları training’e girmez.

37. Corpus manifest

Pipeline sonunda corpus manifest yazılır.

İçerir:

  • corpus ID
  • source project
  • dump date
  • source URLs
  • expected checksum
  • observed checksum
  • verification status
  • parser versions
  • Git commit
  • config hash
  • synthetic dataset manifest hash
  • document count per stage
  • filtering counts
  • duplicate counts
  • contamination counts
  • train/validation counts
  • artifact SHA-256 hash’leri
  • warnings
  • finalized status

Phase 1 sonunda:

finalized = false

çünkü tokenization ve final token budget henüz yapılmadı.

38. Phase 2 corpus tokenization

Phase 2 henüz implement edilmedi.

Burada GPT-2’nin pinned tokenizer’ı kullanılacak.

Temiz training documents:

clean + train split

tokenize edilecek.

Tek deterministic token stream üretilecek.

Bu stream’den:

  • 10M token
  • 25M token
  • 50M token

cutoff’ları alınacak.

Bunlar üç bağımsız random corpus olmayacak.

10M ⊂ 25M ⊂ 50M

olacak.

Document separator olarak EOS token kullanılacak ve EOS da token budget’a dahil edilecek.

39. Neden 10M / 25M / 50M?

Amaç büyük ölçekli Türkçe model pretraining yapmak değil.

Amaç:

Türkçe adaptation strength arttıkça transfer nasıl değişiyor?

sorusunu ölçmek.

10M:

  • düşük adaptation

25M:

  • orta adaptation

50M:

  • güçlü adaptation

condition olarak kullanılabilir.

Böylece Turkish adaptation amount ile:

  • Turkish perplexity
  • English forgetting
  • Turkish factual retrieval
  • cross-lingual transfer

arasındaki ilişkiyi görebiliriz.

40. M2 ve M3 budget matching

M2 ve M3 karşılaştırmasında toplam training budget eşit olmalı.

Örneğin M3’e Branch B Turkish sentence eklersek M3 daha fazla toplam token görmemeli.

İki seçenek var:

Seçenek A

M3’te generic Turkish token miktarını azaltıp Branch B repetition eklemek.

M2 = 25M generic Turkish
M3 = 24M generic Turkish + 1M Branch B repetition

Seçenek B

M2’ye equal-size neutral Turkish filler eklemek.

Daha temiz seçenek genelde A’dır.

Ana prensip:

  • optimizer step aynı
  • token budget aynı
  • batch size aynı
  • LR schedule aynı
  • starting checkpoint aynı

olmalı.
